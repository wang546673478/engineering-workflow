# 真实会话基线查询试点：用户体系梳理

日期：2026-10-24
项目场景：用户指定的既有工程用户体系梳理会话（公开版省略会话 ID 与内部仓库/路径信息）
目的：验证新工作流能否按对象 ID 快速取回当前基线事实，并据此判断是否能量化整场工作的时间/调用节省。

## 真实项目只读查询

在目标项目现有 manifest、带源码哈希的 GORM/Gin 来源回执及 schema-only SQLite 快照上，运行一次 `workflow_state.py query`，按 6 个对象 ID 读取 4 个数据库表切片和 2 个固定路由切片。该次命令耗时 0.8965 秒，6 项均返回 pass。查询只检查离线源码/schema 来源，没有读生产业务行、执行在线 handler 或认证线上权限。路由上的权限说明来自静态来源回执，不代表部署后的授权行为已验证。

另一个重复计时试验把同一查询运行 10 次，中位耗时为 0.9205 秒。这是查询性能样本，不是会话总耗时，也不与旧会话做了配对比较。

### 公开版去标识测量数据

| 测量项 | 结果 |
| --- | ---: |

| 读取生产业务数据行 | 否 |

## 结论与下一步测量

本次实测确认：当项目已有可用来源回执、对象 ID 受当前查询适配器支持时，一次 CLI 调用可在约一秒内返回多个带来源的事实切片。它减少了这次样本中人工分别定位文档/源码的步骤，但没有记录足够的反事实基准，不能给整场“当前用户体系”梳理计算节省时长或百分比。

要测算总体收益，应选同类、范围清楚的完整任务，分别保留旧流程与新流程下的宿主工具调用日志、实际操作时间、重试/失败及交付验收结果；最好做配对回放，并把用户等待、推理时间和实施测试分开。没有这样的样本前，整体时间节省和百分比保持“未验证”。
