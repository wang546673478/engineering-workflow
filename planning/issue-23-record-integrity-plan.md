# PLAN-ISSUE23-RI-01：权威工程记录的全局保存架构

状态：candidate / draft；基于当前已接受事实基线 `BASELINE-ISSUE23-02` 和候选需求 `SPEC-ISSUE23-RI-01`。不属于 `PLAN-ISSUE23-01 r1`，没有复用其实施批准。

## 根因模型

这不是单个命令拼错所能解释的完整故障。现有系统将复杂状态放在可直接覆盖的 Markdown/JSON 文件中；当前 Task 又同时承担“当前状态”与“仅此文件拥有的历史”。编辑通常可从 shell/Python 直接写文件，缺少保存版本、并发前置条件、独立恢复副本和统一写入边界。Git 只在内容已受跟踪且历史被保存时有帮助，不能保护未跟踪 Task，也不能恢复尚未提交的内容。原有 approval digest 绑定审阅内容，但不是存储副本，不能恢复被覆盖字节。

因此，只增加“写前复制”“禁止某个命令”或“写后检查行数”不会形成全局保证：单条错误内容可以被完整、原子地写入；操作也可以绕过约定命令；备份若与原件同一生命周期，仍可能一并丢失。

## 架构候选

### 建议：宿主拥有的版本化工程状态服务，项目文件为受控视图

引入由实际 agent 宿主提供的本地状态 owner，以及项目内兼容适配器。权威 owner 提供稳定的项目/文档 ID、不可变内容 revision、追加式操作记录、当前 head 和只读历史查询；工作区中的现有 Markdown/JSON 可继续供人阅读，但由 owner 安全更新或再生成。每次写入带 `expected_revision` 并表达目标变更；原文件绝不作为唯一历史。批准记录引用不可变审阅 revision 和范围。

写入事务顺序：验证目标和父 revision → 持久化新内容对象及审计事件 → 原子提交新 head → 更新项目视图。启动/恢复时可从已提交 head 重建视图；若视图与 head 不符，隔离差异并恢复视图，不接受差异覆盖历史。并发编辑采用 compare-and-swap，冲突显式提交给编辑者合并。恢复旧版本是新的 head/restore event，不删除中间记录。

真正的“不能绕过”需要宿主控制写权限：受管工作区对 agent 的任意文件写 API/命令只读，专用 writer 暴露受约束编辑能力。单独安装脚本、文件 watcher、Git hook 或 SKILL/AGENTS 指令都无法在 agent 仍有 unrestricted shell/file write 时提供硬保证；若宿主不能提供隔离，产品承诺降为“检测和可恢复”，验收中标为部分支持。

状态服务至少保留两种不同故障域中的可恢复副本，例如宿主本地状态目录作为主存储、项目侧加密/受控快照作为恢复副本；具体位置、所有者、加密、权限、清理和保留期必须按宿主实际能力验证。默认不做云备份。此建议不假定 SQLite、Git 或任一实现已经被选择。

### 备选及取舍

| 方案 | 优点 | 根本缺口 | 结论 |
| --- | --- | --- | --- |
| 仅在 Skill/AGENTS 强调安全编辑 | 迁移容易 | 依赖模型记忆；绕过 shell 写入；没有独立版本/并发/恢复 | 不足以修复本 bug |
| 仅给每次编辑加本地副本或原子替换 | 能保留部分旧内容、减少截断 | 不能阻止完整错误文本替换；同盘删除/并发覆盖仍在；revision/批准不关联 | 作为写入器内部保障，而非总体架构 |
| 对所有 Task/文档强制 Git commit | 已提交内容可追溯 | 不能覆盖未提交误写、未跟踪文件、非 Git 项目；高频保存负担；提交审批混合 | 不作通用权威存储 |
| 宿主版本化状态服务 + 项目格式适配器 | 能覆盖非 Git、跨文件恢复、并发检测和明确授权绑定 | 需要宿主 write boundary；隐私/存储生命周期与迁移需设计 | 建议候选 |

## 范围与职责

1. **宿主平台**：项目身份、持久化状态 owner、追加/原子保存、版本查询/恢复、agent 工具权限隔离、清理与恢复 UI/API。此处是阻止任意写入绕过的唯一有效责任边界。
2. **本 Skill 仓库**：定义文档 ID/revision 与批准绑定合同、文件型项目适配器要求、迁移/兼容行为和诚实的 unsupported 报告；不伪称自己能控制宿主 shell。
3. **工程检查器**：验证 manifest 指向的记录 revision/摘要、主存储与物化文件的对应关系、未记录差异、备份能力状态；如宿主不支持能力则显式 partial/unsupported，不能仅看文件存在。
4. **项目**：选择是否启用服务及本地保留/加密政策；初始化或采用时记录历史起点、权威位置与恢复方式。没有批准不自动迁移旧项目。

## 对当前 Skill 流程的影响

预期影响是保存和恢复机制变化，业务治理流程保持。正常使用时，当前四层工件链与用户审核节点继续运行：持续记录需求仍可照常保存；保存生成的技术版本只说明“记录内容变了”，不等于需求确认、模块审核、Spec 冻结、方案批准或实施授权。语义 revision 只在各自审阅边界真的变化时递增；不为每次提问新增审核轮次，也不改变已批准 Issue #23 的 T23-01..08 范围。

对既有项目，兼容分两种状态：尚未迁移时继续按原有 Markdown/JSON、manifest 声明和当前检查门槛运作；迁移必须先展示映射、文件跟踪/未跟踪状态、可导入历史与无法恢复的缺口，再由项目选择启用。迁移不自动把 diagnostic 改为 strict，不增删 required checks，不改变小修、有效批准复用或基线审阅例外。旧批准仍只绑定原范围；导入旧记录不伪造新的用户批准。

有一项可见的操作变化：**已迁移并启用强制写入边界的项目**，受管记录可能变成只读视图，编辑需经专用 writer；并发版本过期时会要求解决冲突后再保存。这影响“怎样编辑和处理冲突”，但不增加“要不要审核”的业务节点。宿主若只能检测而不能阻止直接写入，则报告降为可发现/可恢复，不能宣称流程强制执行。宿主边界、迁移体验和冲突如何呈现仍需确认；此结论当前为候选设计，不是已验证的宿主能力。

批准摘要仍保留其原职责：证明批准所审的 Spec/Plan 内容和范围；状态服务负责保存与恢复。整合时须保留 Issue #23 已批准的 diagnostic/strict、approval reuse、顺序证据、原检查与超时合同。系统 revision 不得被误映射成批准 revision。

| 流程部分 | 候选影响 | 保持项 |
| --- | --- | --- |
| Baseline / Spec / Plan / Task | 工件可从权威状态恢复，revision 增加机械保存层 | 工件含义、顺序和当前指针关系不变 |

## 实施顺序建议（仅在本 Plan 获批准后）

## 实施顺序建议（仅在本 Plan 获批准后）

1. **P-RI-01 宿主能力盘点**：确认本地任务/Workspace 实际写 API、shell 沙箱、持久化目录、权限、崩溃语义、多 agent 共享、跨重启与清理。宿主没有正式接口时，将宿主工程作为独立依赖和阻塞，不在 Skill 内制造虚假强制措施。
2. **P-RI-02 不可变版本核心**：先建立项目/文档/revision/event 语义、保存事务与 CAS；用合成项目覆盖“正确文档被整篇替换”“写到一半进程退出”“两个 writer 同时提交”“回滚/恢复”。
3. **P-RI-03 强制边界与视图**：通过宿主权限只读挂载受管文件，专用 writer 更新结构化状态并渲染现有格式；绕过写入要在文件系统层拒绝，若无法实现就明确标成仅检测。
4. **P-RI-04 批准和复用**：把现有 approval subject 从工作区易变字节映射到状态服务的不可变 revision/内容 digest，保持旧 contract 的时间、source、scope、REQ/AT、有效复用和 strict/diagnostic 语义；不重开未变的用户批准。
5. **P-RI-05 历史查看与恢复**：提供按文档查看版本、恢复某版为新 revision、查看差异/事件及重建状态指针。恢复绝不改写/删除事故来源。
6. **P-RI-06 旧项目迁移**：预览项目中现有权威路径、Git跟踪状态、外部历史和大小；建立逐字当前快照，记录不可恢复的历史缺口；仅在用户或项目策略授权下迁移。file-only、Git、untracked、无仓库各自有明确流程。
7. **P-RI-07 运维和发布**：验证 retention、加密、权限、备份损坏/缺失、host upgrade/downgrade、重装与删除。若远端同步没有用户明确请求则保持禁用。

## 验证和未决事实

需要真机故障注入，而不只 mock：整篇错误覆盖、短写、磁盘满、宿主崩溃、重启、两个并发 agent、把当前视图删除、主存储或副本丢失、加密/权限边界、非 Git 项目迁移。性能与留存评估使用项目文档规模，不用单个事故虚构阈值。

仍需宿主调查：实际文件写权限是否能按目录约束；终端与 editor 是否共用进程权限；agent 任务/分支间状态能否共享；备份是否超出本机；服务重装和账号切换会否丢失；用户能否独立导出/删除。以上不能由当前 Skill/Python 源码推断。

审批影响：该架构增加宿主状态 owner 和 workspace 权限边界，扩大 1.8.0 skill/checker 的既有范围；其目标是保护现有工作流，而非更改审核合同。批准后仍需更新 Baseline、Spec/Plan/Task、模块地图、契约、业务流、版本/CHANGELOG；protected rules 按当前 control-plane 路径单独审阅。现在没有用户批准，不实施代码、hook、host 设置、迁移或发布。
