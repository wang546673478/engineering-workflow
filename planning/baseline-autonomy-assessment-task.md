## 用户确认：动态基线原则

2026-10-17 03:23（Asia/Shanghai），用户原话：“还有一点我要提出来,就是关于程序基线的审核,肯定不是一次性就能完成,那么在后续的软件测试,功能模块修改,发现基线文档不正确的情况下也应立即更改,这个是动态的过程,不是静态”。确认范围为持续维护基线这一需求原则；没有将其扩展为对前轮全部候选方案的批准或正式实施授权。

已核实：现有SKILL正文要求代码变化同步模块/契约/数据库/业务流，并规定资料与代码冲突时先查证；implementation-workflow要求证据绑定源码/工作树、受影响旧报告转为历史。现有规则已覆盖部分持续性，但未清楚规定“源码未变、后续测试或调查发现既有文档误解”也独立触发主动校正，更未完整说明错误推翻既有方案依据时如何处理。

后续方案应落实以下边界：

1. 当前基线随已证实的认知和程序版本持续更新。首次审阅确认针对当时的版本、范围和证据；后续发现错误不会因“已审核”而保留在当前权威描述中。
2. 测试、运行、代码阅读或模块修改发现冲突后，立即标记受影响结论并查证；一旦证实，agent主动修正文档，不等待用户再次要求。证据不足时保留冲突及待验证项，不将猜测改写为新事实。
3. 校正同步追踪受影响的模块地图、接口、数据库字典、业务流、清单/映射及当前Spec/Plan/Task；即使本轮没有改产品源码，也适用。以已确认需求核对实现和测试，不能为使测试通过而改弱断言或改写业务要求。
4. 保存发现原因、旧结论/新结论、源码或工作树版本、验证依据、影响范围和当前状态；原审阅记录作为历史保留，不能将旧批准悄悄移植到新内容。
5. 事实性文档更正由agent直接完成。若错误改变业务决定、权限/计费规则或已批准方案依据，及时告知用户，标记受影响批准需要复核，暂停依赖错误结论的实施；只重新审核受影响部分，独立且仍有效的工作继续。

这是用户已明确提出的持续维护原则及其建议落实方式，不要求把首次调查无限延长；首次应交付有界且可审阅的基线，之后持续纠错与增量验证。

## 已核实发现

### 1. 多次结束回合，仍有可继续的已知调查

最新会话中，用户明确选择先补齐基线后，又多次发送“那就继续”“一次性补齐吧”“继续”“那就完成全局基线”。agent 分别补完接口批次、插件证据、消费者候选与高风险回归后结束回合，仍列出后续调查。能够分批保存和汇报不代表需要重新取得继续调查授权。

正文已要求“源码可查的信息自行调查”“先完成可独立开展的梳理”，但缺少明确的持续执行循环、环境准备默认职责和可操作停止条件。执行不足与指令不够明确同时存在；不能据此断言所有停止都由 skill 强制造成。

### 2. 技术语义核验被称为人工确认

会话把逐字段含义/读写方、逐接口响应/权限/消费者等列为“人工核验”；用户因此追问开源系统如何由自己确认。project-documentation 的 semantic/manual review 是需要理解源码的核验，正文没有规定全部必须由人类用户逐项执行。

agent 应自主追踪源码、测试、迁移和运行证据，清楚标记推断和真实未知；用户最终审阅基线范围、结论和限制。基线审阅仍是现行阶段门槛，不应将其解释为用户对全部源码事实、生产正确性或合规性的保证。

### 3. required manual inventory 无可达的通过路径

本仓库 `scripts/check_project.py` 的 inventory 分支明确：`provenance.type == manual` 一律 partial；非完整来源也为 partial。后续 pass 分支只支持数据库元数据来源，没有通用 contract/route 来源适配器。`references/checker.md` 第76行亦明确 manual 永远 partial。

外部项目却把 database-source 和 route-source 声明为 required；已有真实数据库运行来源另列为 database-runtime-source。最终报告仍有 baseline not complete 和两项 manual/partial。补调查、反复运行测试或用户接受基线，都不能单独让 manual 分支通过；只改 type/complete、删除必需项或自行填写批准同样不合法。

这是证据模型/适配能力与完成门槛的结构冲突，需要给出真实、受支持且适用于目标范围的验收路径。它不能包装成用户还未认真审核，也不能靠调弱检查来消除。完整版清单示例同样将 routes 列为 required，应在未来方案中复核初始化与能力匹配。

### 4. 自主数据库准备实际可行，本案已有实例

已有 PREP 验证产物记录：agent 从官方源下载 MySQL 8.4.10 归档，在任务临时目录启动独立实例；复用本机 PostgreSQL 二进制并建立独立数据目录/端口；完成 SQLite、MySQL、PostgreSQL 的既有 fresh/代表性 upgrade/重复初始化及独立日志库测试，并停止临时实例。

## 候选规则与关联影响

以下为本轮建议，尚未作为用户确认或实施批准：

1. **自主执行闭环**（instructions / takeover）：基线调查获得授权后，持续按覆盖清单调查、准备环境、验证、补文档和复核剩余缺口；批次保存与进度汇报后继续。只在可审阅基线已形成，或真实缺少用户决策/权限/凭据/工具而无法继续相关工作时停下；独立工作仍应推进。
2. **隔离环境默认职责**（instructions / implementation）：需要数据库、缓存、运行时或锁定依赖时，自主选择项目已有方案、局部工具、便携实例或已可用容器，安装、启动、验证并记录清理。全局安装、系统服务/配置变更、共享业务环境或实际不可用权限需要按适用规则单独处理；不能把局部准备等同于业务实现或生产部署。
3. **核验职责清楚**（instructions / documentation）：源码与测试能回答的技术问题由 agent 核验；只向用户提出真正无法调查得到的业务决策和访问事项。最终基线审阅提交整体结构、关键链路、覆盖和限制，不要求用户逐字段担保。
4. **有界基线与可达验收**（instructions + checker + templates）：先明确版本/工作树、当前系统范围和必需证据；区分结构覆盖、agent语义复核、运行验证、外部环境未知和用户范围接受。已知缺陷可以是基线事实；调查不自动升级为修复全部历史缺陷、所有供应商接入或生产合规认证。适用项目规则仍优先。

第4项涉及目前的强完整性文本、provenance 能力和门禁语义，不能只追加“自主”二字。未来可评估真实源适配器，或保持 manual/partial 如实报告并另设有证据的基线审阅机制；两者均需完整设计与独立批准，不能提前视为已选方案。

延后项：验收机制选型（模块 checker，依赖兼容性/可信来源/项目既有必需检查，恢复条件为正式方案）；端到端行为验证（模块 instructions，场景至少包含缺数据库、长调查、多批保存、共享服务限制、manual来源、生产集成不可用，恢复条件为候选规则定稿）。旧融合方案继续暂缓，与此处的自主性改进没有默认依赖。
