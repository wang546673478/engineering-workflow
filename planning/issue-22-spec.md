## 1. 这次要达到的效果

让使用现有 skill 的 agent 更容易说明三个问题：缺陷是否真的修好、本批交付是否落实了已确认目标、需求有没有说清触发条件和可观察结果。

增强服务于维护者、项目使用者和执行任务的 agent。它只细化现有流程中的记录、核对和表达方式，延续项目自己的工具、术语、权威文档与验证方式。

审核本 Spec 要确认的是下面的目标、范围和验收边界。文件如何组织、具体修改清单和实施顺序由后续 Technical Plan 说明；Spec 的确认与实施授权继续按原规则分别记录，同一条明确指令仍可覆盖其实际表达的批准范围。

## 2. 当前已经有什么

- 已有接管、基线审阅、需求访谈、完整方案确认、实现与验证，以及小修、空实现项目和恢复复用的适用路径。
- 已要求缺陷先复现并定位；测试、运行或源码证据可以推翻错误的现状认识，并回写 Baseline、Plan 和 Task。
- 已有交付前收敛：将代码事实与批准的需求、方案、任务和验证证据对应起来。
- 已有需求/验收 ID、追踪关系、模块审核及候选、确认、延后的区分。
- 检查器核验声明、路径、状态和实际命令结果，不能自动证明业务语义、测试充分或人类批准真实。

这次补强的是操作指引和表达示例。全局事实与原有审批证据仍以原权威资料为准，不因增加模板而重新定义。

## 3. 整体范围与流程保持约束

### REQ-ISSUE22-E01：保持现有流程及其适用边界

增强前后，相同项目、目标、影响范围和已有授权应选择相同的流程路径，保留：

1. 首次接管的全局梳理、基线审阅与完整方案批准顺序。
2. 小修按既定需求及最小必要影响分析执行的路径；缺陷分类不替换 `small_fix` 的规模语义。
3. 已有有效基线、原批准与恢复上下文的复用；不因新会话或模板升级重复访谈和审核。
4. 空实现起点、首批实施后的 partial 事实基线、交付前 complete 基线的原生命周期。
5. 需求确认、方案批准与实施授权的不同含义，以及仅重审受影响部分的规则。
6. 自主调查、事实纠错、继续独立有效工作及原有停止条件。
7. 原验证命令、必需检查、完成门槛、提交保护与外部批准语义。

三项增强均嵌入原有节点，不产生新的阶段、固定审批轮次或交付门禁。不得通过“模板推荐”“默认可选”等措辞，实际强制新报告、新字段或新命令。增强也不赋予提交、推送、发消息、发布、部署或修改外部项目的权限。

## 4. 增强一：缺陷证据更清楚

### REQ-ISSUE22-E02：在原记录中保存可追溯的缺陷证据

出现缺陷时，在项目已有 Task、Issue 或影响记录中，按实际影响整理支持判断所需的最少信息：

| 要回答的问题 | 适用信息 |
| --- | --- |
| 发生了什么 | 症状来源、期望与实际、受影响用户或行为 |
| 在什么条件下发生 | 相关源码/工作树版本、环境、输入/状态与复现步骤 |
| 为什么发生 | 已证实的原因、对应证据，以及尚未证实的假设 |
| 准备改变什么 | 原因对应的修复范围、调用方/数据/权限影响及需要保持的行为 |
| 实际验证了什么 | 修复前后结果、相关回归或适用核验、未验证项及残余风险 |

这些是指引，不是每项小修都要填齐的固定表单。允许合并、引用已有记录，清楚说明真正不适用的内容；不为同一事实另建平行台账，也不把固定文件名或 BUG 工件设为前提。

### REQ-ISSUE22-E03：结论与真实证据一致

区分“已复现”“未复现”“无法运行”“原因假设”“已证实原因”和实际修复结果。没有复现不等于报告无效；完成诊断也不等于获得修复授权。

修复有效的结论应能回溯到原症状的前后核验和受影响行为的验证。不能只因文档与代码一致、模板填完、测试总数增加或任意测试通过就宣布缺陷已解决。采用受控等价场景时说明它覆盖了什么、与原环境有何差异；未覆盖的关键条件仍保持未验证。

已声明必需验证的失败、跳过、缺工具或不支持，继续按原规则记录为未满足，不用一个自填 verdict 或“不适用”理由将其改成通过。

### REQ-ISSUE22-E04：验证与修复影响相称

优先复用能实际观察该问题的现有测试或核验。有必要新增回归测试时，使它能识别对应缺陷，并在修复后检查预期行为；同时关注修复不能破坏的受影响行为。

不强制所有任务采用 TDD，不为低影响文字调整、模板变化或其他可逆小修一律新增测试。验证方式遵循项目规则、实际产物及影响；文档问题可以用适用的内容、链接和场景核验。人工核验只证明实际观察的范围，不能冒充未执行的自动化或运行验证。

调查发现是需求变化、现状记录错误或测试期望错误时，先按原权威关系查证和纠正，不修改测试或需求来掩盖程序缺陷。

## 5. 增强二：已有交付前收敛更具体

### REQ-ISSUE22-E05：核对本批目标、实际实现与证据

在原交付前核对中，针对本批交付范围及其受影响调用链，检查：

- 已确认需求或验收在本批应完成，实际实现是否缺失或只有一部分。
- 实现是否与批准的需求、方案或需要保持的行为矛盾。
- 本次新增/改变的行为是否有需求归属，或已有有效的技术调整依据。
- 验收证据是否对应实际源码版本、环境与行为，是否存在未验证或过期证据。

核对覆盖 Baseline → Spec → Plan → Task → Code/Evidence 的关联，并检查实现和证据对上游事实的反馈。范围外的未来需求、已明确延后事项和有效的历史实现不自动变成本批必须完成的工作。

保留项目现有的收敛记录位置。发现差异后继续在已有授权内调查、处理和复核，不强制创建独立 converge 报告、执行新命令或增加一次人类审核。没有发现差异不等于获得超出实际范围的正确性证明。

### REQ-ISSUE22-E06：差异回到正确的权威层处理

| 发现 | 处理方式 |
| --- | --- |
| 现状事实记错 | 查证后更正 Baseline 及关联视图，保留旧证据和原批准范围 |
| 技术细节调整，用户行为不变 | 同步 Plan、Task 与实际影响文档 |
| 本批实现没有满足已批准目标 | 在现有范围与授权内修复、验证并回写事实 |
| 新目标、权限、范围或验收 | 形成新 Spec revision 或变更请求，只重审受影响部分 |
| 新增实现缺少需求归属 | 先调查已有依据和消费者，记录是否超范围；不自动补造需求、删除实现或批准扩大范围 |
| 某项证据无法取得 | 记录真实限制、影响及下一步；保持必需项未满足，继续独立有效工作 |

不能为取得“已收敛”结果静默修改已批准 Spec、弱化验收、清空延后项或把未完成改成完成。

## 6. 增强三：可选的结构化表达

### REQ-ISSUE22-E07：EARS 作为需求表达参考

EARS 是把“在什么条件下，系统应有什么可观察行为”写清楚的句式。新增或修订需求可按需要选择以下表达，也可继续采用项目已有的中文、表格或其他格式：

| 类型 | 中文等价句式 |
| --- | --- |
| 始终成立 | 系统应当…… |
| 事件触发 | 当……发生时，系统应当…… |
| 状态约束 | 在……状态期间，系统应当…… |
| 异常处理 | 如果……异常发生，那么系统应当…… |
| 可选能力 | 在启用……能力的情况下，系统应当…… |
| 组合条件 | 根据实际需要组合适用条件，并明确系统响应 |

例如：“当用户提交空输入时，系统应显示校验提示。”句式不替用户决定提示内容、权限或其他未确认规则。

不要求历史需求统一改写，不强制英语或 SHALL 关键词。始终型没有独立触发条件是合法表达；句式符合格式不证明内容完整、规则正确或已经获得确认。

### REQ-ISSUE22-E08：Given–When–Then 作为验收示例

验收可使用“已知什么前置状态 → 执行什么操作 → 应观察到什么结果”的表达，例如：“已知输入为空，提交后，应显示校验提示且不保存无效数据。”

保持原需求 ID、验收 ID、状态、来源与追踪关系；它们仍在项目原权威文档中维护。采用示例不意味着新增测试框架、解析器或自动化执行能力，也不把语法通过当成业务验收通过。

### REQ-ISSUE22-E10：增强内容一致且验证范围真实

后续实现应同步实际受影响的指令、引用、模板和本仓库 Baseline/Spec/Plan/Task，不引入互相冲突的当前规则。内容按阶段加载，避免在多个文件复制同一套规则。

保持原检查声明和强度；验证既包括适用程序检查，也包括能暴露“新增阶段/重复批准/强制模板/扩大范围”的行为场景。不得以只匹配文案、标题或关键词的测试宣称流程等价。

按项目原版本规则评估最终交付 diff 的版本及 CHANGELOG 影响。本次仅提供 Spec 草稿，不修改技能版本，不把计划中的增强描述成已实现、已验证或已发布。
