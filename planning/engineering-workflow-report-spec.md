# SPEC-ENGINEERING-WORKFLOW-REPORT-01：实战报告改进的通用规则

状态：已批准实施（2026-11-01，Asia/Shanghai）。

批准证据：用户确认按完整方案实施；批准不扩展到外部项目、固定语言适配器或项目专用工具实现。

## 目标

在不改变既有工程流程、审批语义和 required checks 的前提下，把报告中已确认有价值的改进整理为可复用的通用规则：恢复时能读取结构化问题状态，环境和工具能力可核验，源码分析有精度和未知边界，验证证据不被错误复用，门禁按项目实际影响维度适用，缺陷诊断保留相关反例。

## 需求

### RPT-01 问题状态

Task 或现有需求记录可以为每个问题保存 `question_id`、`status`、`asked_at`、`answer_ref`、`scope` 和 `resume_condition`。恢复时先读取状态，只对状态允许继续询问的问题追问；已回答或尚未满足恢复条件的问题不得因为上下文恢复而重复发问。此字段不创建新的审批、阶段或门禁。

### RPT-02 环境契约

项目可以在 manifest 或其链接的环境证据中声明逻辑工具标识、版本、定位方式、校验信息、用途、缓存/隔离策略和状态；实际路径、版本探测结果和校验结果写入当前 Task 的环境证据。Skill 只定义字段和诊断语义，不固定任何可执行文件名、操作系统路径、数据库、语言或版本。工具缺失、版本不匹配或能力不足必须报告为 `unavailable`、`unsupported` 或 `unverified`，不能伪造通过，也不能自动降低 required checks。

### RPT-03 工具选择与项目专用维护

工具选择遵循“现成工具优先；没有适用工具或能力不足时，允许维护项目专用工具”。采用项目必须记录工具来源、版本、覆盖范围、维护责任和验证方式。Skill 不把某个项目的工具实现提升为所有项目的必需组件。

### RPT-04 源码分析适配器

源码分析通过语言/框架适配器提供。每个适配器声明输入、精度等级、关系类型、覆盖范围、排除范围、版本、源指纹和限制。关系可以包括正向/反向引用、调用、类型/接口实现、构建或运行时依赖、版本元数据、生成/过滤索引和动态未知关系；具体关系是否可观测由适配器声明。核心分析由确定性的解析器、编译器或其他已声明工具完成，不依赖大模型；模型可以帮助解释结果，但不能替代分析证据。默认交付证据使用适配器能提供的精确全量分析；分析不能证明的部分保留 `unknown/unsupported`。

### RPT-05 增量结果边界

增量或缓存结果只用于开发阶段的快速反馈。最终验证、交付报告和需要完整依赖图的结论必须重新执行适用的精确全量分析。缓存只有在源指纹、配置、工具版本和范围未变且没有新反例时才可复用；跨工作树或输入变化不得复用旧结果。

### RPT-06 验证报告和结果复用

验证报告绑定精确提交/工作树、源指纹、工具环境、命令、范围和 required checks。项目允许的报告位置由 manifest 或项目规则声明；同一树的复用必须显式记录来源和适用范围，跨工作树不得复用。记录类变更不得静默跳过 required checks；任何复用都不能降低或替代现有门禁。

### RPT-07 影响维度和门禁分级

门禁适用范围由项目 Baseline、manifest、`documentation_impact`、Task 声明的影响维度和现有规则共同决定。Skill 不预设业务领域分类。开发阶段可以使用聚焦检查，但交付阶段仍执行项目声明的 required checks；安全规则、用户决定和实际适用的必需检查不因规模变小而自动豁免。

### RPT-08 缺陷诊断纪律

缺陷调查需要把症状、条件、已证实原因、应保持的行为、修复后结果与修复范围相关的对照现象/反例连接起来。无法解释的相关现象必须标记为未验证或待查；不要求为每个小修复解释与范围无关的所有现象，也不新增固定表单或诊断审批。

### RPT-09 已有流程和恢复规则保持

现有 Baseline、Spec、Plan、Task 的职责、用户审核节点、恢复时的适用重读、required checks、控制面保护和未知状态保持不变。已经覆盖的恢复最小重读规则不重复新增；本 Spec 只补充明确缺口。

### RPT-10 明确非目标

本批不增加凭据处理规则，不把任何特定项目事故、固定目录、固定语言、固定业务类别或固定工具路径写入通用 skill；不迁移外部项目，不自动修改项目工具，不把效率统计变成 required gate。

## 验收

- **AT-RPT-01**：恢复 fixture 能依据结构化问题状态避免重复提问，并区分已回答、待回答、阻塞和已关闭。
- **AT-RPT-02**：环境 fixture 能报告可用、缺失、版本不匹配和不支持，且不会降级 required checks。
- **AT-RPT-03**：工具选择 fixture 证明现成工具优先，并能记录项目专用工具的来源、覆盖和维护责任。
- **AT-RPT-04**：至少一个适配器 fixture 能返回精确全量关系（包括其声明支持的正向/反向、类型/接口、构建或生成关系）、源指纹、版本、覆盖范围和限制；无法观察的关系为 `unknown/unsupported`，且结果不依赖大模型调用。
- **AT-RPT-05**：源或工具输入变化后，增量结果不能作为最终证据；最终验证重新执行精确全量分析。
- **AT-RPT-06**：报告复用只在同一精确树和声明范围内生效，跨树结果被拒绝或标记不适用，required checks 语义不变。
- **AT-RPT-07**：门禁分级来自项目实际影响维度，示例不包含固定业务领域；聚焦检查不能替代交付 required checks。
- **AT-RPT-08**：缺陷 fixture 能保留相关反例的未验证状态，不强迫解释无关现象。
- **AT-RPT-09**：原有流程、审批、阶段、required checks 和控制面回归保持通过。

## 批准边界

本 Spec 只批准通用规则和接口方向。具体适配器、项目专用工具、manifest 字段迁移和验证命令须在 Plan/Task 中按采用项目实际情况声明；本 Spec 获批不自动授权实施这些具体内容。
