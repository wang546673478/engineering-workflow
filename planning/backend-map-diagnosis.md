## 用户确认的规则

用户提出：“只要涉及到功能模块的变动，都应该进行讨论记录需求”；延后讨论也应写入文档，并在后续恢复；执行完整性与内容遗漏需要用户审核。

讨论后用户确认第1、2点，要求将第3点的集中核对与模块用户审核合并，并明确：“我也同意你说的需求状态和实施状态分开记录”，选择“每个功能模块讨论完成后审核一次”。据此形成以下确认范围：

| 事项 | 确认规则 |
| --- | --- |
| 触发 | 功能模块新增、修改、删除及行为、权限、计费或数据关系变化的讨论均记录，不等到编码；已采用任务后续回答无需再次点名skill |
| 记录 | 讨论中持续维护同一权威需求与当前状态，区分事实、候选、确认和待讨论项，复用条目，避免重复台账 |
| 延后 | 保留所属功能、已有结论、待决问题、影响/依赖和恢复讨论条件，进入依赖它的设计或实施前回看 |
| 审核 | 模块讨论收敛后集中核对需求、变化、待定/延后及关联影响，再由用户审核，保存所审版本、原话和范围 |
| 状态 | 需求状态与实施状态分开；记录、确认需求和批准实施不是同一动作 |

审核按模块进行，记录仍随讨论持续进行；不每轮另设集中检查或重复索要审核。用户需求确认不自动批准编码，现有基线审阅与完整实施方案批准仍保留。

用户先要求讨论而不修改，随后明确“按照讨论记录开始改吧”，批准上述范围的本地实施；完成后又要求“上传到github”。实施和本次发布批准均由TASK-CONTINUITY-01记录，不复用旧发布任务授权。
