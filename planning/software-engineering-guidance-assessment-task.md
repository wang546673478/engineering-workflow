## 研究结论

### 可直接抽象到整个软件工程

1. **先检索、再复用、最后新增**：改动前搜索现有模块、业务封装、调用方和测试；新增替代实现必须记录能力缺口及不能复用/组合/扩展的原因。它能加强现有“检索现有能力”和职责集中要求，适用于前后端、CLI、数据库和文档工具。
2. **行为优先的测试边界**：新增功能、缺陷和行为变化必须有对应回归；优先保护用户行为、稳定接口或明确回归路径，避免只测渲染/日志/代码运行；测试应覆盖相关成功、边界、失败和恢复路径。Bug按“稳定复现 → 修复 → 回归”记录，但不把强制TDD扩大到所有低风险改动。
3. **测试隔离与确定性**：fixture最小且有业务含义；每个用例独立初始化/清理缓存、存储、mock、定时器和测试数据；异步等待明确状态，不使用固定sleep、执行耗时或顺序依赖；只mock不可控外部边界，不mock被测模块，也不复制生产逻辑计算期望值。该内容与本skill此前的隔离环境和真实验证职责直接一致。
4. **错误归属与契约保持**：保留原始API/错误契约，明确错误由请求层、业务层、页面/调用方还是全局边界处理；避免重复提示和把失败当成功；日志不得泄露凭据或完整敏感错误对象。可加入改前影响分析和验证记录。
5. **发布前质量闭环**：按影响范围运行受影响测试、类型检查、lint、格式化、构建和必要的产物/环境检查；不以一项通过替代其他适用检查；提交说明和变更文档同步。现有 skill 已有部分要求，可补成更清晰的“检查选择与证据”协议。
6. **规范本身的更新闭环**：重大规范变化同步项目入口、文档和变更记录；这与当前动态基线校正原则一致。

### 跨软件领域的实际对应

| 通用原则 | 前端示例 | 其他工程领域的对应 |
| --- | --- | --- |
| 搜索已有业务能力，解释新增理由 | 复用确认弹窗，而非只用了Button就宣称复用 | 后端复用授权/计费服务；数据库复用已有事务/查询入口；CLI复用参数、重试和输出能力 |
| 保护行为与契约 | 点击/键盘/错误状态回归 | API响应与权限；数据库约束/迁移/回滚；后台任务幂等/重试；CLI退出码/输出格式 |
| 测试隔离与确定性 | 清理store、mock与定时器，等待实际界面状态 | 隔离数据库/缓存/队列；可控时钟和故障注入；异步消费等待可观测状态 |
| 明确失败处理归属 | 一次操作失败只由负责层提示 | 服务边界保留原因、安全错误码和日志；消费者处理重试/死信；CLI返回准确失败码 |
| 风险与交付物决定检查 | 焦点、键盘、语言切换和响应式 | 数据兼容/并发/一致性；协议兼容；基础设施配置/恢复；数据管道输入输出质量 |
| 依赖和交付证据 | 新库评估，构建与产物核对 | 第三方服务/SDK/系统工具的版本、维护、许可与运维成本；部署包、迁移脚本和恢复验证 |

这些是通用方法与示例映射，不意味着每个项目都必须执行所有领域的检查。

### 与现有skill的增量

现有skill已经覆盖需求/方案、现有能力检索、职责/数据owner、跨层失败恢复、实际检查和动态文档闭环。附件最有价值的增量是把“质量好”落到可观察的实现行为：按用途搜候选并读调用例；复用业务行为而不止底层工具；新增实现写能力缺口；测试保护真实契约且隔离可复现；明确错误处理与敏感日志的负责层。不能把现有条款换个说法再堆一层同义规则。

### 按产物类型抽象后借鉴

- **开发前复用审查**应成为通用的“现有能力检索/替换理由”字段，适用于组件、API、服务、数据库访问、CLI、任务、测试工具和文档自动化，而不是强制所有项目使用组件目录。
- **可访问性与安全**应作为按产物类型触发的检查维度：UI任务检查语义结构、键盘、焦点和状态可达性；认证/敏感数据任务检查服务端校验、秘密、错误泄露和跨站请求；不要求非UI工具套用前端标准。
- **依赖与构建**应要求读取项目权威脚本/锁文件、评估新增依赖维护/许可/体积/安全影响，按项目规则运行构建；不规定 Bun、Rsbuild 或某个命令。
- **组件/模块边界**可转化为“交互、业务规则、持久化、协议和自动化职责保持单一owner，扩展现有能力前先查找调用方和兼容性”，适用于前端组件、后端服务、数据库适配器、消息消费者和脚本。

### 留在项目规则或技术栈专用 skill

- React、TypeScript、TanStack、Zustand、React Hook Form、Zod、Tailwind、Bun、Rsbuild、Vitest、React Testing Library、`useTranslation`、`queryKey`、`beforeLoad`等前端库、目录和命令，以及后端/移动端/数据工程各自的专用库、目录和命令。
- `props`是否解构、单文件约200行、固定80%覆盖率、特定组件路径、固定语言码和组件文件命名。这些可能是好约定，但依赖项目现状，不能成为通用工作流硬规则。
- `useMemo`/`useCallback`、懒加载和虚拟列表等性能建议，应由技术栈规则和测量结果决定，不能把猜测性优化写入通用流程。

### 不直接采纳的风险

- 把所有规范改成硬门禁会造成与本次 `manual/partial` 类似的不可达门槛；应先声明适用条件、证据和项目实际命令。
- 固定覆盖率目标可能鼓励无意义测试；应以业务路径、风险和回归证据为主。
- “每次都必须”执行全套 typecheck/lint/build 可能对大型仓库成本过高；应按影响范围选择，并保留必要的完整门禁。
- 组件复用规则若没有搜索证据字段，容易变成口头要求；若有字段，应让 agent 记录候选、能力缺口和最终选择。
- 对“所有行为改动都必须新增测试”“仅外部边界能mock”“不得sleep/随机输入”需要保留工程判断：复用或更新有意义的现有回归，小型低影响修改选适用验证；依赖隔离可用受控替身，测试对象和关键契约应走真实路径；超时/退避与并发性质本身可测试，但不能靠任意等待或无依据随机数凑覆盖率。
- 附件技术细节也应查证：Rsbuild与`VITE_`变量命名是否对应实际项目配置、分层翻译键和英文fallback键是否采用同一项目约定，都不能直接当作通用标准。任何最终暴露给客户端的配置都不应用来保存服务端秘密。
