## 问题和证据

该工作流把当前状态、持续需求、决策历史、交付进度和恢复依据集中放在项目可编辑文档中。代码仓库的版本控制可能没有覆盖未跟踪/未提交的规划文件；文档编辑也没有一个统一的事务式写入入口。Issue 评论称，一次整文件写入把当前权威 Task 替换为测试文本，之后依靠其他文档重建，独有历史无法恢复。会话审计进一步证实：编辑者通过普通 shell/Python 文件写操作维护这些文件；已有检查器读取清单和声明的文件，但不承载项目状态、不提供文档历史或阻止 shell 直接写入。

已确认的是事故报告、重建状态和当前备份缺口；覆盖前确切写命令、原文全部内容以及是否存在编辑器/系统级副本，仍需在原设备环境中查证。完整恢复旧内容不是本 Spec 可保证的能力。

## 目标

让工程工作流的权威状态有独立、可验证、可恢复的版本来源；每次保存是可识别的状态转移，审批固定绑定审阅对象；常见误写、进程中断和并发编辑不得静默销毁上一版。该机制适用于有 Git 与无 Git 项目。

## 候选需求

- **REQ-ISSUE23-RI-01 — 单一权威源。** 项目声明的工程状态应有明确的权威存储与 owner。工作文档是权威记录或该存储生成的可恢复视图，不能出现多个互相竞争、却都被称作“当前”的来源。
- **REQ-ISSUE23-RI-02 — 不可变历史。** 每次成功保存生成新的、带父版本和内容摘要的 revision；旧 revision 不原地覆盖。版本记录至少能识别项目、文档、revision、时间、来源操作和内容。
- **REQ-ISSUE23-RI-03 — 事务保存。** 持久化历史、更新当前指针和投影文件之间定义崩溃一致性；失败恢复到上一条完整 revision，或明确报告待修复状态，不能把半写文件当作当前权威版本。
- **REQ-ISSUE23-RI-04 — 写入边界。** 受管权威记录通过一个有版本前置条件的写入入口更新；检测到绕过该入口的文件变化时，不静默接受为新权威状态。能否阻止任意 shell 写入由宿主权限/工具边界保证；技能文字与提交检查单独不算强制隔离。
- **REQ-ISSUE23-RI-05 — 并发冲突。** 写操作声明所基于的 revision。若另一 agent/编辑器已保存新 revision，系统应拒绝盲目覆盖并提供可审核的冲突合并。
- **REQ-ISSUE23-RI-06 — 审批绑定。** 需求审阅、方案批准和实施授权引用不可变文档 revision/内容摘要及范围。恢复或重放旧内容会创建新事件，但不自动把旧批准转移到新 revision。
- **REQ-ISSUE23-RI-07 — 可恢复操作。** 用户/agent 可查看历史并从有效旧 revision 恢复。恢复作为新 revision 记录来源，不删除事故、被覆盖版本或失败尝试。
- **REQ-ISSUE23-RI-08 — 修订语义分离。** 系统保存级 revision 与模块审核/Spec/Plan 的语义 revision 分开；同一需求访谈中的进展可可靠留痕，不因此伪造多次正式审核。
- **REQ-ISSUE23-RI-09 — 有界迁移。** 已有项目可从当前文件建立初始快照；迁移明确哪些旧历史可用、哪些已缺失，不推测或伪造丢失历史，不改变原授权/检查要求。无 Git 项目亦可用；Git 历史作为来源之一而非唯一恢复机制。
- **REQ-ISSUE23-RI-10 — 隐私与保留。** 备份范围、访问控制、保留期、清除方式和是否离开本机必须明确；默认不把秘密或工程状态发送云端。
- **REQ-ISSUE23-RI-11 — 工作流连续性。** 记录系统版本只表示保存状态发生变化，不表示需求确认、模块审核、方案批准或实施授权。Baseline → Spec → Plan → Task、当前审批节点、有效例外、必需检查与旧项目兼容保持不变；只有单独审核并批准的流程变更才能改变它们。

## 不在目标内

- 声称哈希、版本控制或完整性检查可以证明内容语义正确、操作者身份真实或所有 agent 遵守。
- 将每次进度保存变成用户批准轮次，或强迫所有项目采用同一种 Git 提交策略。
- 在本任务中实施云同步、修改工作区安全权限、自动迁移外部项目、发布远端 Release 或改变已完成 Issue #23 的 1.8.0 流程合同。

## 验收标准

- **AT-ISSUE23-RI-01：** 整篇误写模拟后，已保存的最新有效 revision 仍可恢复，且当前摘要能指出误写 revision。
- **AT-ISSUE23-RI-02：** 强制终止/磁盘写失败发生在保存流程各阶段时，重启后只出现完整旧版或完整新版，不出现指针和内容相互矛盾。
- **AT-ISSUE23-RI-03：** 两个编辑者基于同一旧 revision 保存时，第二个提交不能无声覆盖第一个。
- **AT-ISSUE23-RI-04：** 从旧 revision 恢复后生成新记录；旧批次的批准不会因此自动应用于新 revision。
- **AT-ISSUE23-RI-05：** 非 Git 项目可以初始化、保存、审阅和恢复；已有 Git 项目不会把未提交/未跟踪规划记录误报成受 Git 保护。
- **AT-ISSUE23-RI-06：** 绕过正式写入入口的直接文件修改有明确且可复现的拒绝/隔离结果；若宿主无法实施，验收明确记录 `unsupported`，不得把指引文本冒充强制保护。当前 Skill 宿主若不提供写入沙箱，只将本地 archive 的检测/恢复能力验证为已支持，并将强制拒绝标记为 `unsupported`。
- **AT-ISSUE23-RI-11：** 操作者从并发保存引发的版本过期冲突可以看见最新 head，不会静默覆盖先保存的 revision。
- **AT-ISSUE23-RI-12：** archive 在创建revision文件过程中发生事务失败后，重启/重试仍只显示之前提交的revision，且旧head保持有效。
- **AT-ISSUE23-RI-07：** 既有纯文件项目可先预览再迁移；初始快照逐字保留当前内容，并明确迁移之前无法恢复的历史缺口。
- **AT-ISSUE23-RI-08：** 本事故可用材料足以把可恢复部分重建到已知状态，同时将不可恢复内容作为明确缺口，不声称完整恢复。
- **AT-ISSUE23-RI-09：** 连续保存多条需求讨论进展只产生记录版本，不自动请求或登记新的模块审核、Spec 冻结、Plan 批准或实施授权。
- **AT-ISSUE23-RI-10：** 未迁移的既有项目继续使用原工件格式、审批语义及已声明检查；迁移先预览并由项目明确启用，不自动打开 strict、增加 required checks 或改变现有阶段。
- **AT-ISSUE23-RI-11：** 过期的 archive head 或并发保存不会静默覆盖先保存的 revision；工具返回冲突并保留双方可见的历史。
- **AT-ISSUE23-RI-12：** archive 事务在版本文件写入期间失败后，重启/重试仍只显示此前提交的完整 revision，旧 head 不被部分推进。
