# 基线与 Spec / Plan / Task 联动模型

本参考定义工程工作流中“现在是什么”和“要改成什么”的边界，以及全局基线、Spec、Technical Plan、Task 和源码验证之间的双向追踪关系。它适用于新项目、首次接管的开源项目、已有文档的旧项目和持续功能变更。

## 术语与权威关系

| 层 | 回答的问题 | 权威内容 | 版本边界 |
| --- | --- | --- | --- |
| Global Baseline | 系统现在是什么 | 模块地图、入口、契约、数据库字典、业务流、缓存/任务/配置、已验证行为、已知缺陷和未验证范围 | 绑定源码/工作树 revision、调查范围和证据；每个修订快照冻结 |
| Spec | 这次要构建什么 | 目标、用户、范围、业务规则、权限、约束、失败行为和验收标准 | 用户确认的需求修订冻结；草稿、已批准和被替代版本分开 |
| Technical Plan | 如何从当前基线达到 Spec 目标 | 方案选择、模块责任、复用/扩展边界、接口、表、迁移、兼容、恢复、验证和依赖顺序 | 绑定 Baseline revision 与 Spec revision；批准后作为本批实施边界 |
| Task | 具体执行哪些动作 | 可执行步骤、依赖、负责人、状态、验证证据、阻塞和下一步 | 实施状态持续变化；每项必须能回溯到 Plan 和验收 |
| Evidence / Convergence | 实际做到了什么 | 测试、运行、源码语义核验、差异和基线修正记录 | 绑定实际源码/工作树和验证环境；不能替代用户需求批准 |

权威方向是 `Baseline → Spec → Plan → Task → Code/Evidence`。发现实现事实或基线错误时允许回流：`Evidence → Baseline`，技术决策回流 `Evidence → Plan`；只有用户目标、范围、业务规则、权限或验收发生变化时才回流到 `Spec`。

## 冻结与版本

“动态”表示有控制地演进，不表示实施中任意改写已批准边界。

- 草稿 Spec 可以在访谈中修改；用户审阅并确认后生成有效 Spec revision。
- 已批准 Spec 在该实施批次内冻结。新增需求或改变验收必须生成下一 revision 或变更请求，并标记受影响的 Plan/Task 需要重审。
- Plan 绑定它所依据的 Spec revision 和 Baseline revision。技术实现细节可以在不改变用户行为的前提下调整，但必须在 Plan 当前摘要和决策历史中同步。
- Task 的状态可以持续更新，但不把任务完成写回成“需求已确认”，也不把实现状态写回成“需求已批准”。
- 被替代的内容保留为历史，标记 `superseded`、替代者、日期、原因和影响；当前摘要只保留有效版本。

建议在 manifest 的 `workflow` 中记录 `active_baseline`、`active_spec`、`active_plan`、`active_task`。每个任务可用 `artifact_links` 指向同一组文档；没有这些字段的旧清单继续按旧兼容路径运行，但新清单应声明它们。

## 首次接管已有实现

1. 读取项目规则和现有资料，先判断是否有有效 Baseline。
2. 没有有效 Baseline 时，先完成全局发现：模块、入口、消费者、契约、表/字段、业务流、配置、缓存、任务和验证环境。
3. 将 Baseline 绑定源码/工作树 revision、覆盖范围、证据和限制，提交用户审阅。Baseline 审阅不是功能方案批准。
4. 在 Baseline 之上建立或修订 Spec；把源码事实、目标、候选、确认和延后分开。
5. Spec 确认后制定 Plan，逐条关联需求、受影响的基线视图、复用点、代码入口、数据和验证。
6. 基于 Plan 拆出 Tasks，供完整方案确认；每个 Task 关联 Plan 项、验收 ID、模块和文档影响。批准前可以规划，不能实施。
7. 实施前再次核对四个 revision 和批准范围；没有完整方案批准不得跳到代码。

## 新项目从零建立基线

先核对仓库、已有代码/脚手架、外部服务和资料。已有可复用实现、框架行为、表或契约的范围必须调查；“缺文档”不能证明没有实现。纯新项目不要求审阅不存在的系统，也不能把目标架构写成当前事实。

| 阶段 | Baseline 当前内容和状态 | Spec / Plan / Task |
| --- | --- | --- |
| 初始化 | `planned`，尚未调查；初始化器不生成审核或完成证据 | 定位已有材料、约束、实施范围与权威检查 |
| 确认无既有实现 | `origin=greenfield`、`status=not_applicable`；记录原因、调查证据、源码/空工作树标识、范围及 `implementation_paths` | 进入需求访谈；Plan 描述目标模块/API/表，明确待实现 |
| 首批实施 | `partial`；写入已实现入口、契约、表和验证；保留未实现/未验证范围 | 依据批准方案实施，每项 Task 关联 Plan 项及验收 |
| 本批交付 | `complete`，有用户审阅时可为 `approved`；绑定实际代码、适用视图、测试及限制 | 核对 Spec 边界、Plan、Tasks 和证据后才能完成 |

这里不适用的是“已有系统调查”，不是永久免除 Baseline。即使没有数据库，也需在对应视图记录“不使用数据库”及依据；不能编造表字段。目标视图可和现状放在同一文档，但必须有明确状态和来源，未实现内容不进入现状事实区。首个可交付切片形成它所声明范围内的事实基线；未来需求留在 Spec/Plan/Task，不强迫一次交付全部产品。

`implementation_paths` 是实际或预定实现位置的非空、非根字面路径列表，例如 `src`、`tests` 或 `backend`、`frontend`。不存在的实现路径仅在上述临时状态可作为计划路径；其余文档仍须存在。新增实现位置时先同步该列表和模块清单。检查器在 `not_applicable` 时检查已声明路径内是否出现文件，不受 exclude_paths 影响；发现文件则要求转入 partial/complete。它不能自动证明项目确实从零开始或发现未声明位置的实现，agent 必须核验全仓库。

`not_applicable` / `partial` 仅允许继续规划和开发，仍执行任务批准、检查及其他门槛；不能用于 handoff，选中 Task 标 complete 时也失败。中途交接使用进度/交接记录并保留未完成状态，不把“交接上下文”误写成交付完成。旧清单无须增加这些状态，已有系统保持 complete/approved 门槛。

## 既有文档整理

流程升级或接管时，先从 manifest/已有入口列出当前 Baseline、Spec、Plan、Task 及受影响视图，对照源码和批准记录核对：

1. 将现状事实、需求目标、技术设计和执行进度归到对应权威位置；可合并文件，不能只靠文件名判断内容。
2. 刷新当前有效摘要、版本、来源、批准范围和下一步；为 Plan 项和 Tasks 建立需求/验收及基线视图链接。文档链接存在不等于 revision 一致或语义正确。
3. 错误事实经查证后更正；需求与方案变化按变更规则处理。无法确认的历史说法标为未验证，不迁移成“已确认”。
4. 旧方案、旧进度和旧审阅保留为带版本的历史或 superseded，指向替代内容；不全局替换旧版本、不重写发布事实、不转移审批。
5. 记录本轮核对范围、迁移/不适用项、未决冲突、验证和限制，运行适用检查。缺关键证据的部分保持未完成。

更新 skill 不会自动迁移所有使用它的项目。每个项目在其已授权范围内核对和整理；不能仅凭本仓库的更新宣称外部项目已同步。

## 持续变更与回流

| 触发 | 首先更新 | 需要同步 | 是否重开 Spec |
| --- | --- | --- | --- |
| 新业务目标、权限、范围或验收 | Spec 草稿 | Plan、Task、受影响基线预期 | 是，生成新 revision 并重新批准 |
| 技术实现、库、表名或路由方案变化，行为不变 | Plan | Task、契约/数据库目标记录 | 否 |
| 实现发现现状基线错误 | Baseline 当前视图 | Plan 假设、Task、受影响批准 | 只有错误推翻了需求前提时 |
| 测试/运行发现代码与目标不符 | Task 证据和 Baseline | Plan 或代码 | 先判断是缺陷还是需求变化 |
| 需求已批准但尚未实施 | Spec 保持有效 | Plan/Task 标为未实现 | 否，不能把未实现写成完成 |

每次回流都要记录旧结论、新结论、触发证据、源码/工作树 revision、影响范围、受影响批准和下一步。只重审受影响部分；仍有效的独立决定继续有效。

## 基线视图的联动门槛

按变更类型同步当前 Baseline：

- 模块边界、入口、调用方、事件或消费者变化：更新模块地图和业务流。
- 路由、请求/响应、权限、缓存或后台任务变化：更新前后端契约和业务流。
- 表、字段、索引、约束、迁移、读写方或事务变化：更新数据库字典、业务流和迁移证据。
- 只有实现细节变化：在影响记录中说明基线视图不适用，并留下检索证据。

代码验证完成后，不能只更新 Task。必须刷新受影响 Baseline 视图，并重新检查 Spec/Plan/Task 的引用、状态和 revision 是否仍一致。

## 可机械检查的追踪关系

manifest 至少应能表达：

```json
{
  "workflow": {
    "active_baseline": "BASELINE",
    "active_spec": "SPEC",
    "active_plan": "PLAN",
    "active_task": "TASK-01"
  },
  "baseline": {
    "status": "approved",
    "evidence": "planning/baseline-review.md",
    "document_ids": ["BASELINE", "MAP", "DB", "CONTRACT", "FLOW"],
    "source_revision": "<git-or-worktree-revision>",
    "scope": "<reviewed scope>"
  },
  "tasks": [{
    "id": "TASK-01",
    "artifact_links": {
      "baseline": "BASELINE",
      "spec": "SPEC",
      "plan": "PLAN",
      "task": "TASK",
      "traceability": "TRACE"
    }
  }]
}
```

检查器可以验证文档 ID、活动指针、文件存在性和任务链接；它不能证明业务语义、用户理解或批准真实性。人工审阅仍需确认当前摘要、历史标记、来源 revision 和代码语义。

## 交付前收敛

交付前按以下顺序收敛：

1. 以实际源码/工作树为准核对代码、契约、数据库、模块地图和业务流。
2. 以批准的 Spec revision 核对行为、范围、权限和验收，不把 Plan 建议当成需求。
3. 以批准的 Plan revision 核对实现方式、迁移、兼容、恢复和验证覆盖。
4. 以 Task 核对每个步骤的状态和真实证据，区分通过、失败、跳过、未验证和阻塞。
5. 更新 Baseline 当前视图和纠正历史；保留旧审阅，不把新证据静默转移到旧版本。
6. 只有四层引用和状态一致后，才允许将 Task 标为完成。

沿用项目已有 Task、追踪和影响记录，在本批范围及受影响调用链内，具体检查以下差异；这些分类帮助执行原核对，不产生独立报告、状态字段、命令或审核轮次：

| 差异 | 要核对的事实 |
| --- | --- |
| 缺失 | 本批应完成的已批准需求/验收没有对应实现或有效证据 |
| 部分完成 | 已有实现只覆盖部分条件、调用方、失败路径或验收；注明实际完成与缺口 |
| 矛盾 | 实现、契约或结果与批准目标、方案或需要保持的行为冲突 |
| 本次实现无归属 | 新增/改变的行为缺少需求或有效技术调整依据；先查原决定、消费者及范围，不补造需求、不自动删除或扩大授权 |
| 证据过期或未验证 | 报告对应旧源码、不同关键环境或未观察目标行为；文档彼此一致也不能替代实际验证 |

先从本批需求/验收追到实现和证据，再从本次变化反查其依据与消费者。未来需求、已明确延后事项和有效历史实现不自动进入本批待办。未发现差异的结论只覆盖实际核对范围。

差异按[持续变更与回流](#持续变更与回流)处理：现状错误查证后回 Baseline；行为不变的技术调整回 Plan，并同步 Task/影响文档；未满足已批准目标的实现，在既有授权内修复验证。只有目标、范围、业务规则、权限或验收改变才重开 Spec，只重审受影响部分。证据暂不可得时记录限制、影响和下一步，必需项继续未满足，独立有效工作继续。不得为了“已收敛”静默改写冻结 Spec、弱化验收、清空延后事项或将未完成写成完成。
