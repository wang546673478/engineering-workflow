# Project Documentation Baseline

For first takeover of a documentation-incomplete project, establish a full baseline and obtain the user's review confirmation before the detailed feature interview, not merely before feature development. Follow the stages and exceptions in [SKILL.md](../SKILL.md). Inventory the actual applicable modules, entrypoints, contracts, all tables and all fields first. Work without frontend/backend/database marks those views not applicable with evidence. Reuse existing documents and link to one authoritative location for each fact. A documented baseline is not approval of a major implementation plan.

Present the whole-system structure, important end-to-end flows, coverage and unverified behavior in plain language before asking for review. Record baseline paths, source revision, semantic review and the user's confirmation in the Task. Creating headings or a list of gaps does not complete the baseline. Future feature decisions can remain unresolved in the target Spec while the current-system baseline is established; do not invent requirements to complete it. Mechanical checks do not establish semantic completeness or user confirmation.

## Greenfield entry and document migration

For a project with no prior implementation, follow [the greenfield lifecycle](baseline-linked-artifacts.md#新项目从零建立基线): document the empty starting state and external constraints, use `not_applicable` only with evidence, move to `partial` as implementation appears, and establish a factual `complete` baseline before delivery. Planned modules, contracts and schemas belong to the target Plan until actually implemented. Existing code without documents requires discovery, including inherited scaffolding and integrations; it is not a no-implementation exemption.

On workflow upgrades, [reconcile existing documents](baseline-linked-artifacts.md#既有文档整理) with source and decisions. Refresh current content, authority, revisions, traceability and next actions; preserve historical releases, superseded plans and actual review scope. Updating the skill does not migrate external projects automatically.

### Current and historical baseline views

Each declared baseline view has a current factual document and a separate history document. Keep the existing current path when upgrading an established project and add a sibling such as `frontend-baseline-history.md`; do not rename every existing document only to add a `-current` suffix.

The current document is the only authority for the latest facts. Its header records the as-of revision, scope, source, evidence boundary, limitations, and a link to its history. It contains current implementation facts, verified behavior, known defects, and open unknowns. It does not retain dated superseded sections merely for narrative continuity.

The history document is non-authoritative. Each entry records the old claim, new claim, trigger, evidence, source/worktree revisions, affected scope, affected approvals or Plan assumptions, supersedes links, and the next action. An empty history file for a new project must contain an explicit `No history yet` marker; that marker is not evidence that the system has been reviewed.

Move target design and user decisions to Spec/Plan/Task. Keep exhaustive inventories, generated indexes, test/runtime receipts, and source extraction under evidence/inventory documents linked from the current view. This separation is a one-time agent-guided upgrade for an existing project, recorded in the existing Task; `adopt_project.py` does not inspect, classify, or migrate baseline prose on every run.

## Autonomous discovery and bounded review

Bind discovery to the source revision and working-tree changes, applicable modules, validation environments and intended baseline scope. Follow entrypoints, consumers, migrations and tests through the whole system. The agent performs code and field-semantic review, reconciles contradictions and gathers runtime evidence; “manual review” means reasoning beyond the checker, not assigning technical investigation to the user.

Maintain one coverage view in the existing Task: accounted-for areas and evidence, remaining investigation, external unknowns, actual blockers and next action. Keep investigating and preparing necessary isolated environments after each saved batch or progress update. A list of remaining work is a continuation plan, not a reason to require another “continue”. End with a reviewable baseline or a concrete blocker that cannot be resolved within available tools, authority and evidence; continue independent work first. Ask only for missing decisions/access that investigation cannot supply.

A reviewable baseline accounts for every applicable entrypoint, consumer, table and field within its stated scope, with semantics and key end-to-end flows supported by source/test/runtime evidence. “Complete” means each applicable declared view has a source, status, scope boundary and impact/limitation statement; it does not mean every view has a supported adapter or runtime proof. An unresolved field meaning or contradictory critical flow remains an investigation gap. Known implementation defects may be baseline facts; discovery does not authorize fixing every defect. Distinguish source coverage from runtime validation and external/production unknowns. Use controlled fixtures or sandboxes where appropriate and report their limits. External integration or certification is required only when the actual task or project rules require it; do not claim it from a local test.

Present the user with the system structure, key findings, covered scope, known defects, unverified boundaries and their effect on the next work. The user accepts that version's scope and limitations, rather than personally verifying every field or certifying correctness. Uncertainty that could invalidate the baseline's conclusions or dependent implementation remains blocking for that part; unrelated external unknowns are tracked with owners, effects and resumption conditions. Scope acceptance cannot turn an unsatisfied required check into pass.

## Inventory capability before gates

Before adopting a manifest, compare each proposed required inventory's provenance and scope with supported checker capabilities in [checker.md](checker.md). A manual source may pass only when its declared source/scope is locatable and the mapping matches the listed objects/fields; its limitation must say that this does not prove there are no omissions inside that boundary. This does not replace semantic review; this checker has no generic contract/route extractor. Do not create an impossible required-source gate by copying an example. New templates leave such inventories optional while database/contract documents and semantic coverage remain required. Make an inventory required only when its actual source has a supported, achievable verification path and the project has reviewed the gate.

In an existing project, keep required declarations and failures intact. An impossible gate is a tooling/acceptance conflict, not evidence that the user has failed to understand the source. Complete independent investigation, prepare a concrete supported-adapter or scoped acceptance proposal with its effect on coverage, and follow that project's control-change approval rules. Repeating the same tests, forging provenance, changing complete flags or silently dropping required items cannot resolve it.

## Required views

- **Global Baseline:** current modules, entrypoints, contracts, tables/fields, business flows, configuration/cache/jobs, verified behavior, known defects, external unknowns, source/worktree revision and evidence scope.
- **Spec:** goals, users, scope, business rules, permissions, constraints, requirements and acceptance IDs, with current requirement state, candidate/confirmed decisions and deferred questions. An approved revision is frozen for its implementation batch.
- **Module map:** each module's responsibility, public entrypoints, callers, dependencies, data ownership, events, cache/config/background-worker dependencies, and isolated/dead-code candidates.
- **Frontend/backend contract:** page action, route/method, request and response fields, validation, auth, errors, loading/retry behavior, and UI state updates.
- **Database dictionary:** every table and field, type/precision, nullability/default, meaning/unit/status, constraints/indexes/foreign keys, writers/readers, lifecycle, sensitivity, snapshot/immutability, transaction/lock/idempotency and migration rules.
- **Business flow:** page -> endpoint -> use case -> table/field -> event/job/consumer, including success, failure, retry, recovery, and permission changes.
- **Plan/Task:** dependency-ordered milestones, affected artifacts, acceptance evidence, requirement and implementation states tracked separately, implementation authorization, current next action and handoff notes. Each Plan names its Baseline and Spec revisions; each Task names its Plan items and affected Baseline views.
- **Traceability:** every active requirement maps to the Spec, Plan decisions map to requirements and baseline facts, and Tasks map to Plan items and acceptance evidence. A manifest may expose these links as `active_baseline`, `active_spec`, `active_plan`, `active_task` and task `artifact_links`.

## Source versus goal

Label every statement as current implementation, simulated/partial, target design, or verified behavior. Cite source paths, migrations, schemas, tests, or runtime evidence. Do not describe a target interface as implemented merely because a page or type exists. Mark code as dead only after checking static references, dynamic registration, reflection, generated code, workers, external calls, and tests.

Functional change discussions update the existing target requirements and current task state continuously, following [requirements-interview.md](requirements-interview.md). Separate facts, candidates, confirmed decisions and deferred discussion; link deferred conclusions, questions, effects/dependencies and resumption conditions. Preserve the current-system Baseline as source evidence rather than rewriting it as the agreed target. Refresh current summaries when decisions change and retain superseded history with clear labels. Keep the approved Spec stable within its batch; propagate accepted changes through a new Spec revision, then reconcile Plan and Tasks.

## Consistency gate

For every changed route, type, table, field, event, permission, or dependency, update the affected views and cross-links. Baseline completion is bounded to the recorded revision, scope and evidence above; all applicable entrypoints, consumers, tables and fields must be accounted for with agent semantic review. Unknowns retain an owner, effects and follow-up task; documenting a gap does not verify it. If scope or a critical conclusion cannot be established, keep dependent feature work pending. Declare `task.documentation_impact` for path-based gates so module/call-chain changes require module map, flow, and contract updates, while migration/schema changes require database dictionary and flow updates. Use the checker for mechanical coverage and agent code review for field meaning and ownership.

The declaration is required for the checker to enforce the gate: it does not infer transitive module or database impact from source paths. A task that changes code under a broad module path must still list the expected connectivity and data-document updates, or record why each gate is not applicable with search evidence.

At the end of a module discussion, combine the requirements completeness check and user review as defined in requirements-interview.md; do not defer saving until that review. A path-based checker cannot detect chat decisions that were never recorded or establish that the user reviewed their meaning. Module review leaves the whole-system baseline and complete implementation proposal gates intact; later changes reopen only the affected parts and dependencies.

Keep architecture constraints and target decisions apart from the current module map. Normal leaf modules, migration tools and test helpers are deliberate isolation, not defects. Distinguish genuinely unreachable code from registered dynamic hooks, externally consumed interfaces, and existing but disconnected features.

## Queryable baseline and correction during implementation

The Baseline is the current factual model for declared modules, database structure and frontend/backend contracts, with source, scope and support boundary. Derive code-recoverable facts on demand rather than maintaining a second hand-synchronized copy; stable IDs should retrieve the affected slice and evidence. Reuse a queried slice while its relevant input fingerprint is unchanged and no new evidence conflicts. After a relevant source change or test/runtime counterexample, query and reconcile only the affected slice before the next action that depends on it. Unsupported extraction is explicit unknown/unsupported, never an empty complete result.

Keep authority singular: Baseline owns current facts; Spec owns confirmed requirement text and user-visible goals; Plan owns technical choices; Task owns current progress, blockers and next step. Other records link to the authority or carry a dated/evidenced summary. One change set may update each affected authority and necessary references together; it must not copy full prose or rewrite unrelated views. A proven factual error can be corrected from evidence. New business rules, permissions or acceptance changes follow the existing user decision and Spec review rules. Routine pending evidence does not stop unrelated work; pause only a dependent action that could implement incorrectly if it proceeds on a contradicted or undecidable fact.

For existing-code feature/takeover work without a trusted complete Baseline, establish the project-declared global map before implementing work that depends on it. “Complete” means each applicable declared view has a source, status, scope boundary and limitation/impact note; an explicit unsupported view is visible but is not thereby adapter-supported. Greenfield work records its empty starting point and constraints, verifies the actual facts its first implementation depends on, then advances the factual Baseline through partial to complete before delivery. Hotfix/minor work need not rebuild the global map but still corrects a proven local Baseline error.

## Continuous correction


The current baseline is maintained throughout testing, investigation and approved development. Its historical review remains tied to the version and evidence actually reviewed. A newly discovered documentation error triggers correction even when product source has not changed.

Immediately flag the affected claims and check source, confirmed requirements, migrations, tests and runtime evidence. Once established, correct the current authoritative Baseline views and follow affected links into Plan assumptions and Task progress. Baseline owns current facts, Spec owns user goals/confirmed requirement text, Plan owns technical decisions and Task owns execution status; elsewhere use references, not a second current truth. Record the old/new conclusion, discovery reason, source/worktree revision, evidence, affected scope and current next action in the existing task/history. Routine evidence/semantic notes stay on the pending list without blocking unrelated work; suspend only the next action that would rely on a disproved or undecidable fact and could thereby implement incorrectly. Preserve contradictory or unverified evidence as open until reconciled; do not rewrite a failing implementation as the desired requirement or weaken a test to match it.

Factual documentation correction proceeds autonomously. If the correction changes a product decision or invalidates an approved plan's premise, notify the user, mark that approval as needing review for the affected scope, and pause only work dependent on the disputed premise. Reuse still-valid approvals elsewhere. Do not apply an old approval to corrected content silently. Revalidate affected conclusions and check citation/source freshness; a documentation-only correction does not require rerunning unrelated full suites unless project policy requires them. On recovery, load the current corrected view and its valid review evidence, not an obsolete snapshot presented as current.
