# Implementation Workflow

## Before editing

Restore the current stage and its transition evidence from the authoritative Task. First takeover without a valid baseline follows [SKILL.md](../SKILL.md): global discovery, user baseline review, detailed feature interview, complete proposal approval, implementation. Do not defer the baseline until coding begins or mistake baseline confirmation for implementation approval. Reuse applicable existing evidence and follow the stated small-fix/new-project exceptions.

Read project instructions and the current Global Baseline, Spec, Plan and Task. The Plan identifies the Baseline/Spec it relies on; the Task identifies Plan items and affected Baseline views. Baseline owns current facts, Spec owns confirmed user goals, Plan owns technical decisions and Task owns current execution state. Search for existing implementations and public callers. Write an impact record with requirement IDs, owners, affected modules/routes/tables/fields, permission and financial effects, compatibility, migration, recovery, tests, and docs.

At the start of every task, inspect the host's available skills catalog, plugin/tool registry, or project-provided skill inventory. Filter candidates against the task's actual deliverables, read each applicable `SKILL.md` and relevant linked guidance, and record the review in the Task `skill_review` field. Each candidate record includes its name or ID, source path/URI, visible version or release date (or `not provided`), review timestamp, decision (`adopted`, `not-adopted`, or `unavailable`), and a concrete fit/conflict reason. Record the catalog scope and evidence when no candidate applies or the host cannot expose a catalog. Repeat the review when task scope, deliverables, or available skills change; do not silently substitute a remembered skill version.

At the start/resume of an edit task, range change or handoff, read the active Baseline/Spec/Plan/Task pointers and recent progress. Reuse already loaded slices while the task/worktree/source fingerprint is unchanged and no new test/runtime/source evidence contradicts them. Reload only affected slices when inputs change or a needed fact is missing; do not reread the whole baseline before each small operation. If a takeover of existing code lacks a trusted complete Baseline, investigate the project-declared module map, database and frontend/backend contracts before implementation that depends on those facts. A greenfield project records the empty starting point and constraints instead of inventing an existing-code map; verify the actual facts its first implementation depends on, then move the Baseline to partial and complete it before delivery. Small approved changes do not repeat the full interview. Record documents and revisions reviewed as an audit trail, not proof that a script can verify comprehension.

Follow the continuous records and module review in [requirements-interview.md](requirements-interview.md) for functional change discussions, including short follow-up answers in an enabled task. Before dependent design or implementation, revisit deferred items, check the requirement state and any implementation authorization that applies to the actual Task, and update only affected Baseline/Spec/Plan/Task views and impact references. Evidence or implementation progress may correct current-fact summaries without changing the Spec goal. If a Baseline claim is contradicted, verify and correct it before the next action that relies on it; continue independent work. A recorded or confirmed requirement is not evidence that code exists or that implementation was authorized.

## Defect evidence within the existing task

For a defect, use the project's existing Task, Issue or impact record to connect the reported symptom to the proposed change and its verification. Reuse links to evidence already recorded. Select the information needed for the actual impact; the following questions are prompts, not a mandatory form or a requirement for a separate BUG document:

| Question | Useful evidence |
| --- | --- |
| What happened? | Report/source, expected versus actual behavior, affected users or operations |
| Under which conditions? | Source/worktree revision, relevant environment and input/state, original reproduction steps and result |
| Why? | Confirmed cause with source/test/runtime evidence; distinguish remaining hypotheses |
| What should change or stay the same? | Cause-related fix scope, affected callers/data/permissions, behavior the fix must preserve |
| What was observed afterward? | Before/after results for the original symptom, relevant regression or other suitable checks, remaining unverified conditions and risks |

Keep “reproduced,” “not reproduced,” “cannot run,” a cause hypothesis and a confirmed cause distinct in the project's vocabulary. Failure to reproduce does not invalidate the report. Diagnosis does not authorize a fix; an already authorized fix does not require another diagnosis approval. Continue the original small-fix or larger-change path according to impact.

Before claiming the fix works, connect its result to the original symptom and affected behavior. Prefer an existing test or check that can observe the defect. Add a regression when needed to detect that failure and protect affected behavior; do not impose TDD or a new test on every reversible wording/link adjustment. For a documentation change, use relevant content, links or scenario checks. If using a controlled equivalent of the original environment, state what it covers and the material differences; uncovered critical conditions remain unverified.

A completed template, matching documentation and code, a larger test count or unrelated passing tests do not establish a fix. Required checks that fail, skip, lack tools or are unsupported remain unsatisfied under the existing rules. If investigation instead establishes a baseline error, a wrong test expectation or a changed requirement, reconcile it with the authoritative evidence and confirmed intent before changing that layer; do not weaken an assertion or rewrite the approved goal to conceal a defect.

## Isolated investigation environments

Within the authorized investigation and project rules, prepare necessary runtimes, locked dependencies, databases and caches autonomously. Inspect available project tooling first, then choose a task-local installation, portable instance, virtual environment or already available container runtime. Install missing local dependencies, start isolated instances and run applicable migrations and tests; absence from PATH is an investigation step, not by itself a user task.

Use dedicated data directories/databases/namespaces, local ports and synthetic fixtures appropriate to the service; a Redis logical DB alone is not isolation from shared-instance commands. Record versions, setup method, relevant commands/results and teardown. Keep credentials out of records and clean up only task-owned processes, databases and test keys; do not treat this as permission to flush a shared service. Preserve any retained environment's purpose and restart/cleanup instructions for resumption.

Global installation, system-service changes, shared/production resources or other actions outside existing authority follow the actual host and project approval rules. If tools, rights, credentials or a required external sandbox cannot be obtained, record the attempted options and concrete blocker, ask for only the missing input and continue independent work. Do not claim a connection or test occurred when execution tools are unavailable. Environment preparation does not authorize product behavior changes or production deployment.

## During editing

Keep each capability in one cohesive owner. Depend on stable interfaces instead of internal details; avoid circular dependencies and duplicate validation, pricing, authorization, or persistence rules. Preserve transaction boundaries and exact-once identities where side effects matter. Add a new abstraction only when its boundary removes real coupling and its owner is explicit.

Use real variability or a concrete coordination problem to justify interfaces and adapters; do not add a layer for every function. A same-purpose replacement names the old entrypoint and when it is disabled or removed. Preserve project money units, precision, tenant authorization and durable side-effect identities; take their values from the project rather than this skill.

### Feedback, verification and progress

After a meaningful implementation slice, run the narrowest relevant project check that can give useful feedback. Diagnose failures while their cause is local, and keep failed or partial results visible. Focused checks support development; they never replace the project's complete required-check set before delivery. Run each declared required check with its existing command, scope and timeout. If later code changes affect a verified result, rerun the affected checks and the required final set under the existing project policy.

Independent checks may run concurrently only when their inputs and mutable resources are isolated. Shared databases, schemas, ports, generated files, build outputs, caches or test fixtures are reasons to serialize unless the project provides separate instances. Keep the exact result for each check; a failure, partial result, timeout or missing tool cannot be hidden by another check passing. Summarize aggregate results deterministically from those individual outcomes.

Reuse same-task baseline slices while their source/worktree fingerprint is unchanged and no new evidence contradicts them. Correct a confirmed factual error as soon as it is established, before dependent work continues. Once implementation stabilizes, perform one complete reconciliation of affected Baseline views and their Spec/Plan/Task links, then run the final required checks. A needed factual correction is not deferred to that convergence.

Report implementation, verification and delivery progress separately using the Task's acceptance items as the denominator. State the completed count, total count and relevant statuses; label the percentage approximate when acceptance items differ materially in effort. Elapsed time alone is not completion progress. Estimate remaining time from measured durations of comparable steps and the known remaining work, separating execution from user or external wait and giving a range or confidence when possible. When comparable evidence is missing, report the ETA as unknown. Treat efficiency measurements as directional unless tasks have comparable scope and equivalent acceptance results; state sample limits and do not claim a savings percentage from unmatched data.

## Change and migration control

For data or contract changes, document forward migration, existing-data behavior, compatibility window, rollback or recovery, and cleanup of the old path. Update consumers in the same task unless a compatibility plan states otherwise. Treat route, response, schema, permission, and event changes as cross-layer changes even when the diff is small.

Before editing, set `task.documentation_impact` for every task that can change module or call-chain connectivity, a frontend/backend contract, or a schema/migration. Use the standard gates for module-connectivity (`module map`, `business flow`, affected `contract`) and database (`database dictionary`, `business flow`); include inventory/mapping documents when the project manifest declares them. If analysis proves a gate is not applicable, record the search scope and evidence in the impact document.

Do not treat a skill recommendation as approval to change scope or bypass project rules. User decisions, repository instructions, security constraints, and required review gates remain authoritative. An adopted skill supplies process or tooling guidance only; record conflicts and the final resolution in `skill_review`.

Reopen only the newly changed product decision and its affected dependencies when the user changes confirmed scope or acceptance. Keep the complete proposal current for a major change, while reusing valid approvals for unaffected parts. Ordinary implementation choices inside an approved task proceed without another permission question. Approval records cite the user's statement, reviewed version and exact scope; never fabricate a human approval.

## Recovery and handoff

On start, resume, handoff, incomplete context or agent change, reread the project rules, manifest, active task, recent progress or handoff, adopted skill source/revision and the unfinished documentation before making edits. Inspect the working tree and current task status, then continue from the recorded state. Do not repeat completed work or discard unrelated changes. A handoff must name the current state, next action, blockers, changed files and exact verification still required. A scope, deliverable or technology change requires a fresh `skill_review` and impact analysis.

Refresh the current stage, requirement state, implementation state, open/deferred items and next action when progress or decisions change; a historical append alone must not leave stale instructions current. Preserve the decision history and prior review scope. Recover deferred conclusions, dependencies and resumption conditions before continuing related work, without asking the user to restate recorded answers.

Bind test evidence to the source version/worktree and relevant environment. Old reports become historical when affected source changes; do not claim a fresh pass. When a test expectation conflicts with implementation, reconcile both with confirmed requirements before updating it; never weaken an assertion only to get green results.

Restore any Baseline corrections and affected approval status as part of this check. Testing, runtime observations and source reading can invalidate Baseline documents without a code edit. Follow [continuous correction](project-documentation.md#continuous-correction): flag, investigate, correct affected views and retain evidence/history; factual corrections do not wait for a separate permission request. Pause only implementation dependent on an invalidated decision or premise and reopen only its affected review. A batch save or report is not a stopping condition while authorized investigation remains actionable.

## Version and changelog before delivery

Record a release impact for each delivery batch: the versioning policy and authoritative source, whether a bump is required, old/target version and classification reason, affected packages and synchronization paths, changelog entries/status, validation and publication evidence. A delivery batch is the set of substantive changes handed off or released together; individual edits and internal commits need not each consume a version. Follow the project's existing no-bump rules; absent those, progress, test evidence or publication receipts that leave the delivered content unchanged can omit another bump, with a recorded reason. Skill behavior instructions, scripts and templates count as delivered content.

Use the project's existing release scheme first, including its rules for 0.x, pre-releases, date versions, generated versions and multi-package releases. When no scheme exists and a three-part version is appropriate, use PATCH for fixes or compatible instruction corrections, MINOR for backward-compatible new capability, MAJOR for incompatible changes; reset lower components when raising a higher component. Select the highest applicable impact across the batch. If a project deliberately has no manually maintained version, record that fact and its actual delivery identifier instead of inventing a VERSION file. An unversioned project needing a new scheme or an unresolved compatibility boundary requires a product decision rather than a silent default.

Inspect the real version source and its consumers before updating. Synchronize only files that actually carry the same release version, using project tools for generated manifests/locks. Respect fixed versus independent package versions; do not bump unaffected independent packages or modify unrelated dependency versions. Check release metadata, package artifacts and user-facing version displays against their authoritative source. Keep historical task/release version evidence intact.

Maintain the project's CHANGELOG or designated equivalent as changes are completed. Explain added/fixed/changed behavior and applicable compatibility or migration effects; a list of edited filenames alone is insufficient. Group unreleased changes under Unreleased (with a target version if the project uses one); use the real release date only when publication occurs. Preserve published history and add a new version for subsequent delivered corrections. This repository's default is a candidate-version / Unreleased heading until publication, then that version's actual date.

Before delivery, compare the batch diff with the changelog, verify version sources and all declared synchronization paths, and record the checks and actual status in the Task. Apply any manifest documentation-impact rules to version/changelog files too. These checks are agent review obligations; the current checker does not infer compatibility, require a bump from arbitrary code changes or validate release chronology automatically. A version bump does not itself authorize a commit, tag, push, hosted Release or deployment.

## Completion evidence

Report the checker gate and independent verification together. State the checker mode/source, report and `required_checks_satisfied`, including required fail/partial/skipped/unsupported and unresolved task dependencies. `errors=[]` only means no recorded configuration/execution errors; it is not an overall pass. Then give actual manual command/environment/source scope and results, retaining initial failures and later reruns separately. Manual success does not fill a skipped checker command or replace its original failed result. Finish with remaining approval/product uncertainty and distinguish this slice from overall project completion.

Before the first implementation edit, confirm that the applicable approval covers the presented Plan, current requirements/acceptance and task batch. Requirements answers do not approve an unseen Plan. In an explicitly strict approval project, use the existing checker with its structured approval contract; keep valid prior scope reuse and the original small-fix/greenfield exceptions. For local account/data resets already within authorized scope, record affected old keys/sessions/ownership/history, backup and recovery conditions in the existing impact record before executing.

For a greenfield project, [move the baseline through its lifecycle](baseline-linked-artifacts.md#新项目从零建立基线) during implementation: record actual modules/contracts/data as `partial`, keep unimplemented design in Plan, and establish `complete` factual views with code and verification evidence before completing the selected Task or using handoff. A provisional lifecycle check can pass for ongoing work without establishing delivery readiness. Existing-project requirements, task approvals, required checks and control-plane protections remain applicable.

After a workflow change, reconcile existing authoritative documents under [the migration rules](baseline-linked-artifacts.md#既有文档整理), including stale current summaries, revision/basis links and historical approval scope. Preserve evidence rather than rewriting old reviews as approval of new content.

Run the project's declared checks and relevant focused tests. Record actual commands/results and distinguish passed, failed, partial, skipped, unsupported, and unverified behavior. Update the affected Baseline views and reconcile Spec/Plan/Task references, statuses and revisions before marking done, using the existing [delivery convergence](baseline-linked-artifacts.md#交付前收敛) to place discrepancies in their authoritative layer. Declare and satisfy documentation-impact gates: module or cross-layer connectivity changes must update the module map, business flow, and affected contract; migration/schema changes must update the database dictionary and business flow. Re-run impact checks after late changes.

Before marking a task complete, verify that its `skill_review` is present and complete, including the catalog source/time, candidate paths and versions/dates, decisions, reasons, and any recheck triggered by scope changes. A missing or stale skill review leaves the task incomplete even when code and tests pass.

Use [checker.md](checker.md) for the manifest and CLI. Optional inventories marked not applicable still need a reason. Required checks skipped, unsupported or failed do not qualify for completion; ask for changed acceptance scope only if the task genuinely cannot progress. CI can invoke read-only checks. `--run-checks` runs the explicit trusted project commands; inspect commands and authorization before enabling it. Scripts cannot prove the quality of a requirements interview or field descriptions.
